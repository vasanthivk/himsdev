# Dr Reddis HealthCare — HIMS Database-per-Microservice Design (PostgreSQL)

Derived from `DrReddis_HIMS_Enterprise_Data_Model.sql` (292 tables). Every table is owned by exactly one service; `core.number_sequence` is cloned locally into each business service. Target: one PostgreSQL database per service (PostgreSQL 15+, EDB Postgres Advanced Server, or Azure Database for PostgreSQL Flexible Server). All scripts were executed successfully on PostgreSQL 16.

## How to run

For each service, create the database and run its script with `ON_ERROR_STOP`:

```bash
createdb -E UTF8 -T template0 hims_patient_access
psql -v ON_ERROR_STOP=1 -d hims_patient_access -f 01_patient_access.sql
```

Deploy `hims_identity_org` first, then `hims_revenue_cycle` and `hims_pharmacy_supply`, then the rest.

## SQL Server to PostgreSQL mapping used

| SQL Server (earlier scripts) | PostgreSQL (these scripts) |
|---|---|
| `INT/BIGINT IDENTITY(1,1)` | `GENERATED BY DEFAULT AS IDENTITY` (allows explicit ids during data migration) |
| `NVARCHAR(n)` | `VARCHAR(n)` (UTF-8 database, so Telugu/Hindi text is fine) |
| `NVARCHAR(MAX)` | `TEXT` |
| columns named `*_json` | `JSONB` (indexable with GIN) |
| `BIT` with `DEFAULT (1)/(0)` | `BOOLEAN` with `DEFAULT TRUE/FALSE` |
| `DATETIME2(n)` + `SYSUTCDATETIME()` | `TIMESTAMPTZ(n)` + `CURRENT_TIMESTAMP` |
| `UNIQUEIDENTIFIER` + `NEWID()` | `UUID` + `gen_random_uuid()` |
| `TINYINT` | `SMALLINT` |
| `ROWVERSION` | `row_ver INTEGER`, incremented by trigger `trg_row_ver` (which also sets `updated_at`) |
| computed column `AS (...)` | `GENERATED ALWAYS AS (...) STORED` |
| `UNIQUE` on nullable columns (NULLs equal) | `UNIQUE NULLS NOT DISTINCT` (needs PostgreSQL 15+) |
| filtered unique index | partial unique index (`WHERE ... IS NOT NULL`) |
| time zone `'India Standard Time'` | `'Asia/Kolkata'` |
| `GO` batch separators | removed |

Each script ends with a `util` schema holding the two trigger functions and a `DO` block that attaches `trg_row_ver` to every table with a `row_ver` column.

## Conventions used in every service database

Owned tables keep their original schema and table names from the enterprise model, so the logical model and the physical databases stay traceable. Foreign keys that pointed to another service's table have been removed and the column is annotated `logical FK -> schema.table [Owning Service]`; the application validates these ids at write time. Foreign keys between tables inside the same service are kept.

The `ref` schema holds eventually consistent copies of other services' data that this service needs for display, validation or pricing (for example `ref.patient`, `ref.practitioner`, `ref.service`). They are filled only by event handlers, carry `source_version` so stale events can be ignored, and never have foreign keys pointing at them.

The `evt` schema holds `evt.outbox` (transactional outbox relayed to Azure Service Bus), `evt.inbox` (idempotent consumer log) and `evt.saga_instance` (state for long-running workflows such as discharge, order-to-cash and cashless claims).

## Deployment order

Create 10 (Identity & Organization) first because it owns organization, branch, department and practitioner data every other service replicates. Then 06 (Revenue Cycle: service catalogue, tariffs, payers) and 05 (Pharmacy & Supply: item and drug masters). The remaining services can be created in any order, followed by an initial bulk load of each `ref` table from the owning service's API before event streaming is switched on.
